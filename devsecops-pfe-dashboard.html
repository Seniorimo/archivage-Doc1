Comprendre le projet en mode débutant

Avant de regarder les outils, il faut comprendre l’idée générale : Jenkins joue le rôle d’un chef d’orchestre qui lance automatiquement les étapes de construction, de test, de scan de sécurité et de décision.

C’est quoi le projet ?

archivage-doc est une application Spring Boot. Elle est construite avec Maven, empaquetée dans une image Docker, puis lancée avec une base MySQL pour être testée comme une vraie application.

Spring Boot Maven Docker MySQL

C’est quoi Jenkins ?

Jenkins automatise le travail répétitif. Au lieu de lancer manuellement les commandes, le pipeline exécute les étapes dans un ordre précis : récupérer le code, compiler, scanner, déployer, tester, décider, publier les rapports.

Pourquoi DevSecOps ?

DevSecOps signifie que la sécurité n’est pas vérifiée seulement à la fin. Elle est intégrée dans la chaîne de développement. Chaque changement de code peut déclencher des contrôles automatiques et produire des preuves.

Lecture simple du pipeline

Imagine une ligne de production. Le code entre à gauche, puis il passe par plusieurs contrôles. Si une étape échoue ou si le gate final refuse le résultat, le pipeline s’arrête. Sinon, les rapports sont publiés et archivés dans Jenkins.

1. CodeJenkins récupère la branche du projet.
2. BuildMaven compile et Docker prépare l’image.
3. ScansLes outils cherchent secrets, CVE et failles.
4. DécisionOPA décide si le build peut passer.
Idée clé : un pipeline DevSecOps ne remplace pas un expert sécurité. Il donne rapidement des signaux, des preuves et un niveau de confiance mesurable.

1. DevOps : faire travailler developpement et operations ensemble

DevOps vient de Development et Operations. Le developpement ecrit le code. Les operations preparent l'environnement ou l'application va tourner : serveur, conteneur, reseau, base de donnees, surveillance et disponibilite.

Dans une organisation classique, ces deux mondes peuvent travailler separement. Le developpeur dit : "sur ma machine ca marche". L'equipe operations repond : "en production ca ne marche pas". DevOps reduit ce probleme en automatisant les etapes et en rendant l'environnement plus reproductible.

A retenir : DevOps sert a livrer plus vite, plus regulierement et avec moins d'erreurs manuelles.
automatisation collaboration livraison continue environnement reproductible

2. DevSecOps : ajouter la securite dans la chaine

DevSecOps ajoute le mot Security au milieu de DevOps. L'idee est simple : la securite ne doit pas arriver seulement a la fin du projet. Elle doit accompagner le code des le debut, automatiquement, a chaque changement important.

Exemple concret : au lieu d'attendre la soutenance ou la mise en production pour chercher des failles, Jenkins lance Gitleaks, Trivy, SonarQube, CycloneDX, ZAP et OPA pendant le pipeline. Les problemes sont visibles plus tot, donc ils coutent moins cher a comprendre et a corriger.

A retenir : DevSecOps ne veut pas dire "tout bloquer". Cela veut dire "rendre le risque visible, mesurable et decide par des regles claires".
security shift-left preuves de securite gate risque visible

3. CI/CD : verifier et livrer automatiquement

CI signifie Continuous Integration, ou integration continue. Cela veut dire que chaque changement de code est verifie automatiquement : compilation, tests, analyse qualite, scans de securite.

CD signifie Continuous Delivery ou Continuous Deployment. Dans ton PFE, Jenkins construit et deploie l'application dans Docker pour la tester. Le principe est de rendre le passage du code vers un environnement executable plus fiable.

Exemple simple : CI verifie que le colis est correct. CD prepare le colis pour l'envoyer ou le deployer.
build automatique tests delivery deployment

4. Pipeline : une suite d'etapes ordonnees

Un pipeline est une recette automatisee. Chaque etape s'appelle un stage. Dans ton projet, la recette ressemble a ceci : recuperer le code, compiler, scanner, generer des rapports, deployer, tester dynamiquement, puis demander a OPA si le build peut passer.

Jenkins affiche chaque stage. C'est important pour comprendre rapidement ou un probleme apparait : build Maven, Docker, Gitleaks, Trivy, ZAP, OPA ou publication des rapports.

A retenir : un bon pipeline n'est pas seulement une liste de commandes. C'est une histoire lisible du controle qualite et securite.
stage Jenkinsfile rapport artifact

5. Conteneurs : lancer l'application dans une boite controlee

Un conteneur Docker est une boite logicielle qui contient ce qu'il faut pour lancer une application. Dans ton contexte, Jenkins tourne dans Docker sur WSL2, construit une image de l'application Spring Boot, demarre MySQL, puis lance l'application pour que ZAP puisse la tester.

WSL2 signifie Windows Subsystem for Linux. C'est une couche Linux sur Windows. Elle permet de travailler avec Docker et des outils Linux tout en etant sur une machine Windows.

Image vs conteneur : l'image est le modele. Le conteneur est l'instance en cours d'execution.
Docker image conteneur WSL2 MySQL

6. Scans de securite : plusieurs regards sur le meme projet

Un scan de securite est une analyse automatique qui cherche un type de risque. Aucun outil ne voit tout. C'est pour cela que ton pipeline combine plusieurs familles : SAST pour le code, DAST pour l'application en execution, SCA pour les dependances, Secret Scanning pour les secrets, SBOM pour l'inventaire et Policy Gate pour la decision.

Exemple : SonarQube peut voir une mauvaise pratique dans le code Java. Trivy peut voir une CVE dans une dependance. Gitleaks peut voir un token dans Git. ZAP peut voir un header HTTP manquant quand l'application tourne.

A retenir : les outils ne remplacent pas la comprehension humaine, mais ils donnent des preuves rapides et repetables.
SAST DAST SCA Secret Scanning SBOM Policy Gate

7. Reporting et monitoring : rendre les resultats lisibles

Reporting signifie presenter les resultats sous forme de rapports lisibles. Dans Jenkins, les rapports HTML Publisher et les artifacts gardent les preuves du build : rapports Gitleaks, Trivy, ZAP, SBOM CycloneDX, resultat OPA.

Monitoring signifie surveiller dans le temps. Dans un pipeline, on surveille surtout si les builds passent, quels stages echouent souvent, si les scans produisent des alertes et si le gate OPA bloque.

A retenir : un resultat non lisible est difficile a defendre. Un bon rapport explique ce qui a ete teste, ce qui a ete trouve et pourquoi la decision est prise.

Cours détaillé : comprendre ton PFE sans prérequis

Cette partie explique le projet comme si tu le découvrais pour la première fois, avec des exemples simples et des mots-clés utiles pour l'oral.

1. Pourquoi ce projet existe ?

Dans un vrai projet logiciel, écrire du code ne suffit pas. Il faut aussi vérifier que le code compile, que l'application démarre, que les dépendances ne contiennent pas de vulnérabilités connues, que des secrets ne sont pas envoyés dans Git, que l'application web ne répond pas de manière dangereuse, et que les résultats sont conservés sous forme de rapports.

Ton projet archivage-doc montre cette logique avec une application Spring Boot. Jenkins joue le rôle de chef d'orchestre. Il lance le build, les scans, le déploiement Docker, le test dynamique avec ZAP, puis le gate OPA. Le but n'est pas seulement d'avoir un pipeline qui passe : le but est de montrer une chaîne DevSecOps capable de produire des preuves.

Exemple très simple : imagine une usine. Le code est la matière première. Maven vérifie que la pièce peut être fabriquée, Docker l'emballe dans une boîte standard, les scanners contrôlent les défauts, OPA décide si la pièce peut sortir, et Jenkins garde le dossier de contrôle.

2. DevOps, DevSecOps et CI/CD : la différence en langage simple

DevOps signifie que les développeurs et les personnes qui exploitent l'application travaillent avec une même chaîne automatisée. Avant DevOps, beaucoup d'actions étaient faites à la main : compiler, copier des fichiers, lancer un serveur, vérifier rapidement si tout marche. Cela créait des erreurs.

DevSecOps ajoute la sécurité dans cette chaîne. Au lieu de dire "on fera la sécurité à la fin", on vérifie tôt et souvent. C'est le principe shift-left : déplacer les contrôles vers le début du cycle pour trouver les problèmes quand ils sont encore faciles à comprendre.

DevOps Automatiser build, test, déploiement et collaboration.
DevSecOps Ajouter secrets, CVE, SAST, DAST, SBOM et policy gate dans la chaîne.
CI/CD CI vérifie le code souvent. CD prépare ou réalise la livraison de façon fiable.
Phrase simple pour l'oral : "Mon pipeline ne se limite pas à compiler l'application. Il automatise aussi des contrôles de sécurité et conserve des rapports pour justifier la décision finale."

3. C'est quoi un pipeline Jenkins ?

Un pipeline est une suite d'étapes automatisées. Dans Jenkins, chaque étape s'appelle un stage. Un stage doit répondre à une question simple. Par exemple : "Est-ce que le code compile ?", "Est-ce que l'image Docker se construit ?", "Est-ce que Trivy trouve une CVE critique ?", "Est-ce que OPA autorise le build ?".

  • Checkout : Jenkins récupère le code depuis Git. Sans code, rien ne peut commencer.
  • Build : Maven transforme le code Java en application exécutable.
  • Docker : l'application est mise dans une image pour être lancée de façon reproductible.
  • Scans : les outils cherchent des risques différents.
  • Deploy : Jenkins démarre l'application et MySQL pour un test réaliste.
  • DAST : ZAP teste l'application comme un utilisateur externe.
  • OPA Gate : une règle décide si le pipeline passe ou bloque.
  • Reports : les preuves sont publiées et archivées.
Erreur fréquente : voir le pipeline comme une simple liste de commandes. En réalité, chaque stage doit produire une preuve ou une décision compréhensible.

4. Docker, conteneurs et WSL2 expliqués simplement

Docker sert à lancer une application dans un environnement plus contrôlé. Une image Docker est comme une recette figée : elle contient ce qu'il faut pour démarrer. Un conteneur est une image en train de tourner.

Dans ton contexte, Jenkins tourne dans Docker sur WSL2, c'est-à-dire une couche Linux sur Windows. Cela permet d'utiliser des outils Linux, des conteneurs, Maven, Trivy, ZAP ou OPA dans une chaîne proche d'un environnement professionnel.

Exemple concret : Spring Boot a besoin d'une base MySQL. Au lieu d'installer MySQL à la main sur Windows, Jenkins peut démarrer un conteneur MySQL, puis lancer l'application dans un autre conteneur. C'est plus propre et plus facile à reproduire.
Erreur fréquente : croire que localhost veut toujours dire la même machine. Depuis Windows, Jenkins et un conteneur Docker, l'adresse réseau peut changer. C'est pour cela que les URLs SonarQube ou ZAP doivent être accessibles depuis le bon endroit.

5. Les outils de ton projet expliqués comme à un débutant

Chaque outil a une mission précise. L'erreur classique est de penser qu'un outil de sécurité peut tout faire. En réalité, la force du pipeline vient de la combinaison de plusieurs regards.

Jenkins

Définition : serveur d'automatisation CI/CD.

Rôle : lancer les stages dans l'ordre et afficher où ça passe ou échoue.

Exemple : il lance Maven, Docker, Gitleaks, Trivy, ZAP et OPA sans intervention manuelle.

Mot-clé : orchestration.

Gitleaks

Définition : outil de recherche de secrets dans Git.

Rôle : détecter tokens, mots de passe, clés API ou credentials exposés.

Exemple : un token GitHub écrit dans un fichier est une fuite potentielle.

Erreur fréquente : supprimer le faux secret de démonstration au lieu d'adapter le gate.

SonarQube

Définition : outil SAST et qualité de code.

Rôle : lire le code source sans lancer l'application.

Exemple : il peut signaler un bug, une mauvaise pratique ou un code smell.

Mot-clé : analyse statique.

Trivy

Définition : scanner de vulnérabilités et dépendances.

Rôle : détecter des CVE dans les composants utilisés par le projet.

Exemple : une bibliothèque Maven ancienne peut contenir une faille critique.

Mot-clé : SCA, supply chain.

CycloneDX / SBOM

Définition : inventaire des composants logiciels.

Rôle : savoir précisément quelles dépendances existent dans le projet.

Exemple : si une nouvelle CVE sort demain, le SBOM aide à vérifier si tu es concerné.

Mot-clé : Software Bill of Materials.

OWASP ZAP

Définition : outil DAST pour tester une application web en fonctionnement.

Rôle : envoyer des requêtes HTTP et observer les réponses.

Exemple : il peut signaler des headers de sécurité manquants.

Mot-clé : black-box testing.

OPA

Définition : moteur de règles policy-as-code.

Rôle : décider si le pipeline peut passer selon les résultats des scans.

Exemple : bloquer une CVE critique inattendue, mais laisser visible une faille volontaire de démonstration.

Mot-clé : gate.

HTML Publisher / artifacts

Définition : mécanismes Jenkins pour publier et garder les rapports.

Rôle : rendre les résultats lisibles et auditables.

Exemple : le rapport ZAP HTML est consultable dans Jenkins, les JSON sont archivés.

Mot-clé : preuve.

6. Comment lire les findings Jenkins de ton projet ?

Un finding est un résultat détecté par un outil. Il peut être grave, faible, volontaire pour une démonstration, ou parfois lié à un problème technique de rapport. Le bon réflexe n'est pas de tout supprimer. Le bon réflexe est de comprendre : qui a détecté, dans quel fichier, avec quelle règle, et est-ce attendu ou non.

  • Gitleaks trouve un secret : vérifier s'il s'agit d'un faux secret pédagogique ou d'un vrai secret accidentel.
  • Trivy trouve une CVE : regarder la dépendance, la version installée, la version corrigée et le niveau de sévérité.
  • ZAP trouve une alerte : regarder l'URL, le type d'alerte et si l'endpoint est volontairement vulnérable.
  • OPA bloque : ouvrir input.json et comparer avec la règle Rego.
  • Rapport manquant : ne pas conclure "zéro problème". Il faut vérifier si le scan a réellement tourné.
Phrase simple pour l'oral : "Dans mon projet, les outils détectent et restent visibles. La décision de blocage est séparée dans OPA pour éviter de confondre une vulnérabilité volontaire de test avec un vrai problème non prévu."

7. Ce qu'un débutant doit vraiment retenir

Le DevSecOps n'est pas une collection d'outils posés au hasard. C'est une logique : automatiser, vérifier tôt, garder les preuves, puis décider avec une règle claire. Ton pipeline montre cette logique avec un cas concret : une application Spring Boot, des scans complémentaires, un déploiement Docker, un test DAST et un gate OPA.

Question 1 Qu'est-ce qui a été testé ?
Question 2 Quel rapport le prouve ?
Question 3 Quelle règle décide si c'est bloquant ?
À retenir : un bon pipeline DevSecOps ne cache pas les problèmes. Il les rend visibles, explique lesquels sont attendus, et bloque seulement ce qui dépasse la règle de sécurité définie.

Le principe Shift-left

Déplacer les contrôles de sécurité au plus tôt dans le cycle réduit le coût de correction et transforme la sécurité en feedback continu.

Code

Les secrets et patterns risqués sont détectés avant livraison.

Build

Les dépendances vulnérables sont visibles avec Trivy et CycloneDX.

Analyse

SonarQube inspecte le code source pour les faiblesses applicatives.

Runtime

ZAP observe l’application déployée comme un attaquant externe.

Gate

OPA décide si le build continue selon une policy claire et versionnée.

Explication simple : sans shift-left, on découvre souvent les problèmes de sécurité très tard, parfois après le déploiement. Avec le shift-left, Jenkins donne un feedback tôt : le développeur voit rapidement qu’un secret, une CVE ou une faiblesse de code existe, puis il peut corriger avant que le risque ne parte plus loin.

Pourquoi OPA comme gate ?

OPA sépare la logique de décision du reste du pipeline. Jenkins collecte les preuves, OPA applique la règle.

package security default allow := false allow if { input.trivy.critical == 0 count(input.gitleaks) == 0 input.zap.high == 0 }
Décision explicable
Le résultat dépend de preuves JSON produites par les scanners.
Policy-as-code
La règle est versionnée, relue et testable comme du code.
Blocage contrôlé
Le pipeline s’arrête si des findings critiques inattendus dépassent le seuil défini.

1. Jenkins prépare les preuves

Les scanners produisent des fichiers JSON ou HTML. Par exemple Trivy produit une liste de CVE, Gitleaks produit une liste de secrets détectés, ZAP produit des alertes web.

2. Le script crée input.json

Le fichier input.json résume les résultats importants : nombre de secrets, nombre de CVE critiques, nombre d’alertes ZAP HIGH.

3. OPA répond true ou false

Si la règle est respectée, OPA renvoie true. Sinon, il renvoie false et Jenkins bloque le pipeline.

Erreurs frequentes et bonnes pratiques

Les pieges classiques quand on decouvre DevOps, DevSecOps et Jenkins, avec la bonne facon de raisonner.

Erreur 1 : croire qu'un scan suffit

Un debutant peut penser : "J'ai SonarQube, donc mon projet est securise". En realite, chaque outil couvre une partie du risque. SonarQube lit le code, Trivy lit les dependances, ZAP teste l'application lancee, Gitleaks cherche les secrets.

Bonne pratique : combiner plusieurs outils et comprendre ce que chacun sait detecter.

Erreur 2 : confondre detection et blocage

Une detection est une information. Un blocage est une decision. Dans un PFE, certaines vulnerabilites peuvent etre volontairement injectees pour prouver que les outils fonctionnent. Le gate OPA doit donc distinguer les findings attendus des findings vraiment bloquants.

Bonne pratique : garder les rapports complets, mais bloquer seulement ce qui viole la policy definie.

Erreur 3 : ignorer les rapports manquants

Si un outil echoue et ne genere pas son JSON, il ne faut pas interpreter cela comme "zero probleme". Un rapport absent peut vouloir dire que le scan n'a pas vraiment tourne.

Bonne pratique : verifier l'existence des rapports et garder une preuve claire de chaque scan.
